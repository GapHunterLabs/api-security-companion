# Feature spec — GENERIC_HIGH_ENTROPY false-positive classifier

This is the single source of truth for how a candidate string is turned
into a numeric feature vector. It is implemented **twice**, once in
`train_model.py` (training, Python) and once in
`SecretFeatureExtractor.kt` (inference, Kotlin) — both implementations
must produce byte-identical output for the same input string. That
identity is checked mechanically by `cross_check_vectors.json`
(generated by the Python side, verified by a JUnit test on the Kotlin
side), not by inspection.

Scope: only called for `SecretFinding.kind == "GENERIC_HIGH_ENTROPY"` —
the case where `SecretDetector.looksLikeARealSecret` already passed
(length ≥ 12, not an obvious placeholder, ≥3 distinct characters,
Shannon entropy ≥ 3.3 bits/char) and no fixed-format regex matched. The
classifier's only job is to further separate real secrets from the
common false-positive shapes that still pass that heuristic (UUIDs, hex
hashes, base64 fixtures, bcrypt fixture hashes, `test_`/`sample_` IDs).

## Why hand-engineered features + a small hashed n-gram bucket, not a
raw character-embedding model

A production classifier embedded in a security-sensitive suppression
path needs its Kotlin/Python parity to be trivially verifiable, not
just "probably the same library version". Hand-engineered numeric
features are plain arithmetic — no library internals to keep in sync
across two languages. The hashed n-gram part adds real pattern-matching
signal beyond hand-crafted features, using a hash function specified
here as an explicit formula (the **Java `String.hashCode()` algorithm**,
which Kotlin's `String.hashCode()` already implements identically on
the JVM — the only place parity work is needed is the Python side,
which reimplements the exact same formula rather than using Python's
built-in `hash()`, which is a different algorithm and salted per
process by default).

## 1. Hand-engineered features (12), in this exact order

Given input string `s` of length `L`:

| # | Name | Formula |
|---|------|---------|
| 0 | `length_capped` | `min(L, 128) / 128.0` |
| 1 | `entropy_bits_per_char` | Shannon entropy in bits/char, same formula as `SecretDetector.shannonEntropyBitsPerChar` (`-Σ p·log2(p)` over character frequency), divided by 8.0 to roughly normalize to [0,1] |
| 2 | `digit_ratio` | count of `[0-9]` / L |
| 3 | `upper_ratio` | count of `[A-Z]` / L |
| 4 | `lower_ratio` | count of `[a-z]` / L |
| 5 | `symbol_ratio` | count of chars that are none of digit/upper/lower / L |
| 6 | `unique_char_ratio` | distinct chars in `s` / L |
| 7 | `is_all_hex` | 1.0 if every char is `[0-9a-fA-F]`, else 0.0 |
| 8 | `is_base64_charset_only` | 1.0 if every char is in `[A-Za-z0-9+/=]`, else 0.0 |
| 9 | `has_uuid_dash_pattern` | 1.0 if `s` matches `^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}$`, else 0.0 |
| 10 | `ends_with_equals` | 1.0 if `s` ends with `=` (base64 padding signal), else 0.0 |
| 11 | `starts_with_bcrypt_prefix` | 1.0 if `s` starts with `$2a$`, `$2b$`, or `$2y$`, else 0.0 |

All 12 values are floats in a predictable, mostly-[0,1] range so no
separate scaling/normalization step is needed downstream (kept out
deliberately — a `StandardScaler` with fitted mean/std is one more
artifact that would need cross-language parity).

## 2. Hashed character-trigram bucket features (64), indices 12..75

- Extract every substring of length 3 from `s` (if `L < 3`, zero
  contribution — no padding).
- For each trigram `t`, compute `h = javaStringHashCode(t)` using the
  exact Java formula:
  `h = 0; for c in t: h = (h * 31 + ord(c)) mod 2^32` (32-bit signed
  overflow arithmetic — see reference implementations below).
- Bucket index: `idx = (h & 0xFFFFFFFF) % 64` (unsigned interpretation
  of the 32-bit hash before the modulo, so both languages agree on
  negative-hash handling).
- Feature `12 + idx` accumulates `1.0 / L` for every trigram that
  hashes into that bucket (frequency, not raw count — keeps the scale
  comparable across strings of very different lengths).

Total feature vector length: **76**.

## Reference formula for `javaStringHashCode` (must match exactly)

Python (no built-in equivalent — implemented from scratch):
```python
def java_string_hash(s: str) -> int:
    h = 0
    for ch in s:
        h = (h * 31 + ord(ch)) & 0xFFFFFFFF
    return h
```

Kotlin: `t.hashCode()` on a JVM `String` already implements this exact
formula (JDK-specified, documented, stable across JVM versions) — no
custom code needed on the Kotlin side, only the bucket/frequency logic
around it. This is verified, not assumed: `cross_check_vectors.json`
includes trigram-heavy strings specifically to exercise this path.
